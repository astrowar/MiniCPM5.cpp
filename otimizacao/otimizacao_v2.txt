## 2. Achei mais diferenças importantes entre nosso kernel e o llama.cpp

A V1 que te passei ainda fazia uma redução horizontal:

```cpp
hsum_i32_8(isum)
```

**a cada bloco de 256 pesos**.

Isso é ruim.

Por exemplo, `down_proj` tem:

```text
6144 / 256 = 24 blocos por row
```

Então cada row fazia 24 reduções horizontais.

No `llama.cpp`, os resultados dos blocos continuam acumulados em registradores SIMD:

```text
block 0 ─┐
block 1 ─┤
block 2 ─┤ → __m256 accumulator → hsum UMA VEZ
...      │
block N ─┘
```

O código AVX2 atual do `llama.cpp` realmente mantém um acumulador `__m256`, converte o resultado inteiro de cada superblock e só faz a redução horizontal no final. 

Além disso, no nosso Q6 V1 fazíamos:

```text
q6 unsigned 0..63
      ↓
subtract 32
      ↓
signed int8
      ↓
sign_epi8
      ↓
maddubs
```

Mas isso é desnecessário.

O formato é:

```text
(q - 32) * scale
```

Então podemos calcular:

```text
q * x * scale
```

com `q` ainda unsigned e depois descontar:

```text
32 * scale * sum(x)
```

Os `bsums` do Q8_K já têm exatamente esses `sum(x)`.

É justamente a estratégia usada atualmente no AVX2 do `llama.cpp`: ele calcula a correção de `-32` do Q6_K usando `bsums`, sem converter cada peso para signed antes do dot product.

# Depois da V2, a próxima otimização que eu faria é mais estrutural

Hoje temos:

   ↓

Estamos quantizando **a mesma `x_norm_` três vezes**.

E depois:

```text
gate_proj:
x_norm FP32 → Q8_K → GEMV

up_proj:
x_norm FP32 → Q8_K → GEMV
```

quantizamos a mesma ativação duas vezes.

O ideal é:

```text
                 ┌── q_proj
x_norm → Q8_K ───┼── k_proj
                 └── v_proj
```

e:

```text
                 ┌── gate_proj
x_norm → Q8_K ───┤
                 └── up_proj
```

Assim, em cada layer:

```text
5 quantizações
↓
2 quantizações
```

Mas existe algo ainda mais importante depois disso: **eliminar as centenas de regiões OpenMP independentes por token e usar workers persistentes**. Seu `forward()` chama `matmul()` sete vezes por layer e ainda abre OpenMP para residual/SwiGLU/norms; são 42 layers. O `llama.cpp` tem uma infraestrutura CPU bem mais sofisticada que apenas um `#pragma omp parallel for` por operação. Seu código atual mostra essas regiões independentes diretamente no hot path.
